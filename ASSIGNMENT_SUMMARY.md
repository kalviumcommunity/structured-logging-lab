# Structured Logging Assignment Summary

## Original Requirements

The assignment asked for the `orders-api` service to be upgraded from vague
plain-text logs to structured JSON logs that are useful during incidents.

- Every log line must include a timestamp, severity, service name, and message.
- Normal events must use `info`, handled oddities must use `warn`, and real
  failures must use `error`.
- Each incoming request must receive a unique request ID and every log produced
  during that request must include the same ID.
- The failing endpoint must be triggered and the logs must be filtered with
  `jq` by severity and then by request ID.
- Before and after log output must be shown as validation evidence.
- `CLOUD_LOGGING.md` must explain how the JSON fields map to a cloud logging
  service such as Google Cloud Logging or Grafana Loki.
- Credentials, tokens, card numbers, passwords, and other sensitive values must
  never be written to logs.
- Work must be completed on `feat/structured-logging` and submitted through a
  GitHub pull request with meaningful commits and validation evidence.

## Changes Implemented

- Replaced the unused logger stub in `src/logger.js` with a JSON logger.
- Updated `src/server.js` with service logs, request ID middleware, request
  start/completion logs, and structured failure logging.
- Updated `src/db.js` to use the request or startup logger and severity levels.
- Updated `src/payment.js` to preserve request context in delayed payment logs.
- Updated `src/routes/orders.js` to log successful, invalid, and failed order
  operations with request context.
- Added `CLOUD_LOGGING.md` with Google Cloud Logging and Grafana Loki mappings.
- Updated `README.md` with the failure-tracing commands.
- Added `.gitignore` entries for `node_modules/` and local log output.
- Added `package-lock.json` generated by `npm install`.

## Implementation Details

### JSON logger

`src/logger.js` defines `createLogger()` and emits one JSON object per line to
stdout. Each record contains `ts`, `level`, `service`, and `msg`. Additional
fields are added as structured properties instead of being embedded in free-form
text. The logger supports `child()` so request context can be bound once and
reused by downstream code.

### Request correlation

Middleware in `src/server.js` creates one `crypto.randomUUID()` value per
request, stores it as `req.id`, and creates `req.log` with the bound `reqId`.
The middleware logs `request.start` and records `request.complete` with the HTTP
method, path, status code, and duration. Route, database, and delayed payment
operations receive and use this child logger.

### Severity levels

- `info` is used for startup, request lifecycle, successful operations, and
  normal payment/database progress.
- `warn` is used for a handled database connection failure and invalid order
  input.
- `error` is used for failed order operations and the `/simulate-error`
  failure endpoint.

Error messages contain only safe diagnostic text. No request body, database
password, token, or payment credential is logged.

### Failure trace evidence

Before the change, the original container emitted unstructured lines after
startup and test requests:

```text
starting
connecting...
done
error
retry
payment started
payment
error happened
ok
done
```

The Docker verification after the change returned HTTP 500 from
`/simulate-error` and produced
this request ID:
`96258b2e-b49d-4f50-8335-011fee2643a4`.

The observed JSON records for that request were:

```json
{"ts":"2026-11-21T05:43:17.826Z","level":"info","service":"orders-api","msg":"request.start","reqId":"96258b2e-b49d-4f50-8335-011fee2643a4","method":"GET","path":"/simulate-error"}
{"ts":"2026-11-21T05:43:17.827Z","level":"error","service":"orders-api","msg":"payment.failed","reqId":"96258b2e-b49d-4f50-8335-011fee2643a4","error":"simulated payment dependency failure"}
{"ts":"2026-11-21T05:43:17.837Z","level":"info","service":"orders-api","msg":"request.complete","reqId":"96258b2e-b49d-4f50-8335-011fee2643a4","method":"GET","path":"/simulate-error","statusCode":500,"durationMs":11}
```

The error record showed the request ID immediately, and filtering all records
with that ID showed the start, failure, and completion story. The commands for
the container evidence are:

```bash
docker logs orders-api | jq 'select(.level=="error")'
docker logs orders-api | jq 'select(.reqId=="96258b2e-b49d-4f50-8335-011fee2643a4")'
```

The source implementation binds one unchanged `reqId` to all request records.

## Work Flow and Issue Resolution

1. **Initial repository mismatch:** The first workspace was
   `cloudnotes-ops-readiness-lab`, not the requested `structured-logging-lab`.
   It had a different Python application, no `orders-api`, and no Docker Compose
   setup. The requested repository was cloned separately and the work continued
   in `C:\Users\zzjzj\Desktop\structured-logging-lab`.

2. **Fork and branch setup:** The assignment required working from a fork. The
   feature branch `feat/structured-logging` was created in the cloned repository.
   The implementation was committed locally before the fork was available.

3. **Initial Docker failure:** `docker compose up -d --build` first failed
   because Docker Desktop's Linux engine was not running. Docker Desktop was
   started, the command was retried, and both `orders-api` and PostgreSQL started
   successfully.

4. **Port conflict:** A local Node process from the earlier non-Docker test was
   still listening on port `3000`, so Compose could not bind the API port. The
   process was stopped and the Compose stack was started again.

5. **Missing jq:** The required `jq` command was initially unavailable. `jq`
   version `1.8.2` was installed with WinGet, and both required filters were then
   executed against real Docker logs.

6. **Container name mismatch:** Compose initially generated the name
   `structured-logging-lab-orders-api-1`, while the assignment required
   `docker logs orders-api`. `container_name: orders-api` was added to
   `docker-compose.yml`, the stack was rebuilt, and the exact assignment command
   worked.

7. **Before/after evidence:** The original commit was run in a temporary
   worktree to capture the old plain-text logs. The updated branch was then run
   in Docker to capture the JSON error and request-ID traces.

8. **GitHub push failure:** A direct push to the upstream repository returned
   HTTP 403 because the account did not have write permission there. A fork was
   created at `arbinbiswal/structured-logging-lab`, the branch was pushed to the
   fork, and the upstream pull request was created from the fork branch.

9. **Pull request description issue:** The first PR description attempt allowed
   shell backticks to be interpreted while using an inline command. The
   description was corrected using a Markdown body file, and the duplicate
   fork-only PR was closed.
